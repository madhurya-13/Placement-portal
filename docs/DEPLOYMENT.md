# Milestone 10 — Production Deployment

| Piece | Service | Why |
|---|---|---|
| Backend (FastAPI) | **Render** | Python runtime, runs Alembic migrations on deploy, health checks |
| Frontend (React/Vite) | **Vercel** | Zero-config Vite builds, global CDN, preview deploys per PR |
| Database (Postgres) | **Neon** | Serverless Postgres with a generous free tier and connection pooling |
| Source of truth | **GitHub** (`madhurya-13/Placement-portal`) | Both platforms deploy from the repo — push to `main` = deploy |

```
 Browser ──► Vercel (static SPA, CDN) ──API calls──► Render (FastAPI + gunicorn) ──► Neon (Postgres)
                 │                                        │
                 └─── VITE_API_BASE_URL                    └─── DATABASE_URL, SECRET_KEY,
                      (build-time env)                          FRONTEND_ORIGIN (CORS), CLOUDINARY_*
```

Everything needed is already in the repo:
- `backend/runtime.txt` — Python 3.12.8
- `backend/requirements.txt` — includes `gunicorn` (production server)
- `render.yaml` — Render Blueprint (build/start commands + env var declarations)
- `frontend/vercel.json` — SPA rewrite so deep links like `/officer-dashboard` survive hard refresh
- `app/core/config.py` — normalizes any hosted Postgres URL (`postgres://…` → `postgresql+psycopg://…`) so Neon's connection string works without editing

## 0. Environment variables (the complete list)

### Backend — set on **Render** (Environment tab)

| Variable | Example / source | Notes |
|---|---|---|
| `DATABASE_URL` | `postgresql://user:pass@ep-xxx.aws.neon.tech/neondb?sslmode=require` | Neon pooled connection string. `sslmode=require` is mandatory. The app rewrites the scheme for psycopg 3 automatically. |
| `SECRET_KEY` | *(auto-generated by the Blueprint)* | JWT signing key. Never reuse the local dev key; regenerate if leaked. |
| `ENVIRONMENT` | `production` | |
| `FRONTEND_ORIGIN` | `https://your-app.vercel.app` | CORS allow-list. **Exact** origin — no trailing slash, must include `https://`. |
| `CLOUDINARY_CLOUD_NAME` | from Cloudinary dashboard | Resume uploads. Missing values break resume upload with 401s. |
| `CLOUDINARY_API_KEY` | from Cloudinary dashboard | |
| `CLOUDINARY_API_SECRET` | from Cloudinary dashboard | |

`ALGORITHM`, `ACCESS_TOKEN_EXPIRE_MINUTES`, `REFRESH_TOKEN_EXPIRE_DAYS` have working defaults — set them only to override.

### Frontend — set on **Vercel** (Settings → Environment Variables, **Vite build-time**)

| Variable | Value | Notes |
|---|---|---|
| `VITE_API_BASE_URL` | `https://placement-portal-api.onrender.com` (your Render URL) | Read **at build time**. If unset the app silently falls back to `http://localhost:8000` — the deployed site will appear "broken" with every API call failing. |

> Secrets live only in the platform dashboards — never in `.env` files or git (`.env` is gitignored).

## 1. Database → Neon (do this first; the backend needs the URL)

1. Sign up at [neon.tech](https://neon.tech) with GitHub.
2. **Create project** → e.g. `placement-portal`, region **AWS Singapore** (matches the Render region), Postgres 16+.
3. Open **Connection Details** and copy the **Pooled** connection string (the host contains `-pooler`):
   `postgresql://user:pass@ep-xxx.aws.neon.tech/neondb?sslmode=require`
   - **Pooled** (PgBouncer) for the web app — many short-lived requests fit Neon's compute limits.
   - **Direct** is only for psql/seed scripts.
4. Keep the string somewhere safe — it goes into Render in step 2.
5. **No schema work needed here**: the tables are created by Alembic on every backend deploy (`alembic upgrade head`), including a brand-new empty database.

> Free-tier Neon **scales to zero after inactivity** — the first request after idle can take ~10–20 s while the compute boots. `pool_pre_ping=True` is already enabled, so existing requests fail cleanly and retry rather than hanging.

## 2. Backend → Render

1. Push the repo to GitHub (Render can only deploy from a remote repo).
2. Render dashboard → **New → Blueprint** → connect GitHub → select `madhurya-13/Placement-portal`.
   Render reads `render.yaml` at the repo root and proposes the service `placement-portal-api`.
3. **Environment variables**: `SECRET_KEY` is generated for you. Paste `DATABASE_URL` (Neon pooled string) and the three `CLOUDINARY_*` values. Replace `FRONTEND_ORIGIN` with the Vercel URL if you already know it — otherwise set a placeholder and update it in step 3.
4. **Apply** — the first deploy runs:
   - build: `pip install -r backend/requirements.txt` (automatic, since `rootDir: backend`) then `alembic upgrade head` → creates every table in the empty Neon database
   - start: `gunicorn -k uvicorn.workers.UvicornWorker -w 2 --timeout 120 -b 0.0.0.0:$PORT app.main:app`
5. Verify: `https://<your-service>.onrender.com/api/v1/health` → `{"status": "ok"}` style response, and `/docs` loads the Swagger UI.
6. (Optional) Seed demo data once, from your machine against Neon:
   `cd backend && DATABASE_URL="<neon-pooled-url>" ./venv/Scripts/python.exe scripts/seed_demo.py`

**Production settings used (from `render.yaml`):**

| Setting | Value | Reason |
|---|---|---|
| Runtime / region | Python / Singapore | Closest region to users in India |
| Root directory | `backend` | Monorepo — Render installs the right requirements |
| Build command | `alembic upgrade head` | Schema migrations on every deploy |
| Start command | `gunicorn … -b 0.0.0.0:$PORT` | Render routes traffic to `$PORT`; must bind `0.0.0.0` |
| Workers / timeout | `2` / `120 s` | Fits free 512 MB; avoids cold-start query kills |
| Health check | `/api/v1/health` | Render restarts instances that fail it |

## 3. Frontend → Vercel

1. Vercel dashboard → **Add New → Project** → import the GitHub repo.
2. **Root Directory = `frontend`** (this is the #1 monorepo mistake — without it Vercel finds no `package.json`).
   Framework preset auto-detects **Vite**; build `npm run build`, output `dist`.
3. Add the environment variable: **Settings → Environment Variables** → `VITE_API_BASE_URL` = your Render URL. Apply to Production (and Preview if you want PR previews to talk to the API).
4. **Deploy**. The build runs `tsc -b && vite build`; the output is a static SPA served from the CDN.
5. Back in Render: set `FRONTEND_ORIGIN` to the exact Vercel URL (e.g. `https://placement-portal.vercel.app`) and redeploy (Environment → Save → Manual Deploy → **Clear build cache & deploy**).
6. Verify: open the site, log in with a seeded account, open the officer dashboard. Hard-refresh on `/officer-dashboard` must still render (the `vercel.json` SPA rewrite handles this).

## 4. GitHub integration

- Both services are connected to the repo: **every push to `main` triggers a production deploy** on Render and Vercel (builds appear in each dashboard's Events/Deployments tab).
- Suggested workflow: work on feature branches → open a PR → Vercel builds a **preview URL** for review → merge to `main` → both platforms deploy production.
  - Preview URLs are on `*.vercel.app` with a different origin than production; add the preview origin to `FRONTEND_ORIGIN` (comma-separated list in `main.py`'s `allowed_origins` needs a code change — or temporarily allow it) if previews must call the production API.
- Render: disable auto-deploy on branches you don't want (Settings → Auto Deploy) — keep it on `main` only.

## 5. Updating after deployment

1. Make changes locally; run the checks:
   `cd frontend && npx tsc -b && npx eslint . && npm run build` and start the backend once.
2. **Schema changes**: generate a migration first —
   `cd backend && alembic revision --autogenerate -m "describe change"`, review the generated file, then `alembic upgrade head` locally to test.
3. `git add … && git commit … && git push origin main`
4. Render picks up the push: installs deps, runs `alembic upgrade head` (new migrations apply automatically), restarts gunicorn. Vercel rebuilds and redeploys the static bundle.
5. Rollback if needed: Render → Deployment → previous → **Rollback**; Vercel → Deployments → previous → **Promote to Production**. Both take under a minute. Roll back the frontend and backend together if an API contract changed.

## 6. Common deployment errors

| Symptom | Cause | Fix |
|---|---|---|
| Deploy log: `ModuleNotFoundError: No module named 'psycopg2'` | Neon URL starts with `postgres://` / plain `postgresql://`, which SQLAlchemy maps to psycopg2 (not installed) | Already fixed in `config.py` (URLs are normalized to `postgresql+psycopg://`) — keep using plain Neon URLs |
| Build fails: `alembic: command not found` or revision errors | Build ran outside `backend/`, or `DATABASE_URL` missing at build | Use this repo's `render.yaml` (`rootDir: backend`); ensure `DATABASE_URL` is set before the first deploy |
| API 400/403 from the browser, works in Swagger | CORS: `FRONTEND_ORIGIN` mismatch | Must be the **exact** Vercel origin, `https://`, no trailing slash; save and **Clear build cache & deploy** |
| Frontend loads, every API call hits `localhost:8000` | `VITE_API_BASE_URL` not set at **build** time (the localhost fallback kicked in) | Add the var in Vercel, redeploy (env vars are baked into the JS bundle at build) |
| Hard refresh on `/officer-dashboard` → 404 | No SPA rewrite | `frontend/vercel.json` already contains the rewrite; if you replaced it, restore the `/* → /index.html` rule |
| Vercel: `ENOENT: package.json not found` | Root Directory not set to `frontend` | Project Settings → Root Directory = `frontend` |
| Render: `Worker failed to boot` / boot timeout | Wrong start command, binding a fixed port, or missing env var | Bind `0.0.0.0:$PORT`; check the environment tab has every required var |
| Requests killed after ~30 s on free tier | gunicorn default timeout vs. Neon cold start | `--timeout 120` is already in `render.yaml` |
| First request after idle takes 15–20 s, then works | Free-tier Neon compute suspended after inactivity | Normal on free tier; `pool_pre_ping` recovers cleanly. Upgrade Neon or keep it warm with a cron ping if it matters |
| `/api/v1/auth/login` returns 500 in prod | `SECRET_KEY` missing/empty, or old tokens signed with the old key | `SECRET_KEY` is auto-generated by the Blueprint; after rotating, users must log in again |
| Resume upload 401s | `CLOUDINARY_*` env vars unset on Render | Paste the three values from the Cloudinary dashboard and redeploy |
| Works locally, "Invalid email or password" for everyone in prod | Fresh production database has no users | Run `scripts/seed_demo.py` against the Neon URL (step 2.6) or register normally (first recruiter still needs officer approval) |
